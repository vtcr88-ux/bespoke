Prepare o projeto atual para funcionar como uma mini plataforma white-label,
composta exclusivamente por:

1. página pública responsiva do catálogo;
2. painel administrativo responsivo;
3. API e banco de dados necessários para sustentar essas duas aplicações.

Preserve a estrutura, o design, os componentes, os motions, as funcionalidades
e o comportamento atual da Bespoke sempre que estiverem funcionando
corretamente.

Não reconstrua o projeto do zero.
Não substitua tecnologias sem necessidade técnica comprovada.
Não implemente uma plataforma SaaS multi-tenant compartilhada.
Não adicione tenant_id às tabelas.
Não implemente um construtor visual drag-and-drop.

A arquitetura desejada é white-label single-tenant por instalação:

- um único código-base reutilizável;
- uma implantação independente para cada marca;
- um banco próprio para cada loja;
- um armazenamento de imagens próprio;
- um administrador próprio;
- credenciais e sessões próprias;
- domínio público próprio;
- subdomínio administrativo próprio.

Exemplo:

lojadocliente.com.br
admin.lojadocliente.com.br

Cada instalação deve utilizar o mesmo core, mas não deve compartilhar dados,
usuários, imagens, sessões ou credenciais com outra marca.

Além da transformação white-label, prepare toda a infraestrutura de aplicação
necessária para uma implantação futura em VPS Oracle.

A configuração real do domínio, DNS, HTTPS, Cloudflare e credenciais será

- não imprimir a senha em logs;
- permitir entrada interativa ou variável temporária segura;
- exigir troca de senha no primeiro acesso quando aplicável.

12.5 — NGINX
────────────────────────────────────────────────────────────

Crie templates de Nginx para:

1. página pública;
2. painel administrativo;
3. proxy da API;
4. webhooks;
5. uploads, quando servidos localmente.

Arquivos sugeridos:

- `infra/nginx/public-site.conf.template`;
- `infra/nginx/admin-site.conf.template`;
- `infra/nginx/api.conf.template`;
- `infra/nginx/security-headers.conf`;
- `infra/nginx/rate-limits.conf`.

Página pública:

- servir `apps/web/dist`;
- usar `try_files` para fallback do React Router;
- aplicar cache longo somente a assets versionados;
- não aplicar cache incorreto ao `index.html`;
- encaminhar chamadas públicas da API;
- impedir acesso a arquivos ocultos;
- impedir acesso a `.env`, fontes do projeto, backups e arquivos internos.

Painel administrativo:

- servir `apps/admin/dist`;
- usar fallback apropriado para React Router;
- encaminhar `/api` para a API administrativa;
- não expor source maps em produção quando não forem necessários;
- permitir futura proteção integral por Cloudflare Access;
- não considerar a URL do painel um mecanismo de segurança.

API:

- proxy para a porta interna da aplicação;
- repassar os headers necessários;
- configurar limites de body compatíveis com upload;
- configurar timeouts controlados;
- bloquear métodos HTTP não utilizados;
- não expor diretamente a porta Node.js à internet.

Preferencialmente, permita que:

lojadocliente.com.br/api/public/*
    → API pública

admin.lojadocliente.com.br/api/*
    → API administrativa

api.lojadocliente.com.br/webhooks/*
    → webhooks externos

Essa configuração reduz a necessidade de CORS amplo e permite utilizar
requisições same-origin no painel administrativo.

Não permita que rotas administrativas sejam acessadas pelo host público.

12.6 — SYSTEMD COMO ESTRATÉGIA PRINCIPAL
────────────────────────────────────────────────────────────

Prepare systemd como estratégia principal para manter a API ativa.

Crie:

infra/systemd/catalog-api.service.template

A unidade deve considerar:

- usuário de sistema não root;
- grupo restrito;
- diretório de trabalho correto;
- arquivo de ambiente externo ao repositório;
- `NODE_ENV=production`;
- `ExecStart` apontando para a API compilada;
- reinício após falha;
- tempo de espera entre reinícios;
- inicialização depois da rede;
- logs integrados ao journald;
- encerramento gracioso;
- limites adequados;
- hardening do serviço.

Quando compatível, avalie opções como:

- NoNewPrivileges=true;
- PrivateTmp=true;
- ProtectSystem=strict;
- ProtectHome=true;
- RestrictSUIDSGID=true;
- LockPersonality=true;
- ReadWritePaths somente para uploads, cache e diretórios necessários.

Não aplique uma diretiva que impeça a aplicação de funcionar sem testar e
documentar.

Documente:

- instalação da unidade;
- `systemctl daemon-reload`;
- inicialização;
- habilitação no boot;
- reinicialização;
- consulta de status;
- consulta de logs;
- rollback.

O objetivo é garantir que a API volte automaticamente após uma reinicialização
da VPS.

12.7 — PM2 E DOCKER
────────────────────────────────────────────────────────────

Não configure simultaneamente PM2, systemd e Docker para executar a mesma API.

Use systemd como caminho principal do deploy nativo.

Opcionalmente:

- prepare documentação alternativa para PM2;
- preserve ou crie Dockerfiles de produção;
- prepare `docker-compose.production.yml` para isolamento futuro entre
  instalações white-label.

Identifique claramente:

- estratégia principal;
- estratégia alternativa;
- arquivos pertencentes a cada estratégia;
- comandos que não devem ser combinados.

Para Docker:

- utilize builds multi-stage quando apropriado;
- execute a API como usuário não root;
- não inclua `.env` na imagem;
- não inclua uploads na imagem;
- utilize volumes persistentes;
- não exponha MySQL publicamente;
- não monte o socket Docker;
- não use containers privilegiados;
- adicione health checks;
- configure restart policy;
- mantenha redes separadas.

O diretório:

- deve possuir proprietário e permissões restritas;

- deve ser separado por instalação;
- não deve permitir execução de arquivos.

O deploy deve preservar:

- imagens de produtos;
- capas;
- logos;
- favicons;
- mídias da Home;
- arquivos necessários à marca.

Se o projeto possuir abstração de armazenamento, preserve-a para permitir
migração futura para OCI Object Storage.

12.10 — BUILD DE PRODUÇÃO
────────────────────────────────────────────────────────────

O fluxo esperado deverá ser validado e documentado:

1. instalar dependências:

   npm ci

2. validar variáveis de ambiente:

   npm run env:validate

3. executar migrations:

   npm run db:migrate:prod

4. executar seed somente quando necessário:

   npm run db:seed:prod

5. gerar builds:

   npm run build

6. validar os artefatos:

   - apps/web/dist;
   - apps/admin/dist;
   - apps/api/dist.

7. iniciar a API compilada:

   npm run start:prod

8. servir os builds estáticos pelo Nginx.

Não execute `npm run dev` em produção.

Não use servidor de desenvolvimento do Vite como servidor público.

Não utilize `vite preview` como processo permanente de produção.

Valide se todas as dependências necessárias em runtime estarão disponíveis.

Caso o monorepo exija dependências de desenvolvimento durante o build:

- execute `npm ci`;
- faça o build;
- avalie `npm prune --omit=dev` somente depois;
- não remova dependências necessárias à API compilada.

12.11 — HEALTH CHECKS E INICIALIZAÇÃO
────────────────────────────────────────────────────────────

Implemente ou consolide:

GET /health/live
GET /health/ready

`live` deve indicar que o processo está ativo.

`ready` deve verificar somente dependências essenciais, como:

- conexão com banco;
- carregamento das configurações obrigatórias;
- acesso ao diretório de uploads.

Não exponha:

- senhas;
- connection strings;
- nomes internos desnecessários;
- stack traces;
- tokens;
- detalhes sensíveis do ambiente.

O Nginx, systemd e Docker poderão utilizar esses endpoints para verificar a
saúde da aplicação.
